# Server-side subscriptions, branded icons, and Drive cloud storage (v2)

This pass reviews the fixes applied in response to the v1 review. All seven issues were addressed: the GET API no longer exposes state-mutating actions, replay protection checks for active subscriptions, the failure handler no longer grants local access when in GAS, the cloud photo grid uses safe DOM APIs, file iteration is bounded at 100, read/delete operations verify Pro tier, and an SVG compatibility comment is present.

**Watch for:** One residual XSS vector remains in new code — the `loadCloudPhotos` failure handler injects `err.message` via `innerHTML` without sanitization (confirmed). The `thumbnailUrl` returned from the backend is just `file.getUrl()` (a full Drive page URL, not an image), so photo thumbnails will fail to render as `<img>` sources (confirmed). The ScriptProperties store for transaction IDs grows without bound and has no cleanup mechanism (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The XSS fix in `renderCloudPhotos` correctly uses `createElement`/`textContent`/`setAttribute`, but the `withFailureHandler` for the same call injects `err.message` into `innerHTML` — inconsistent with the fix applied one function away.

The `thumbnailUrl` field returns `file.getUrl()`, which is a Google Drive web page URL, not a direct image link. The frontend sets this as an `<img src>`, so the photo history grid renders no images — only filenames and delete buttons.

Every `generateTransactionId()` call writes to ScriptProperties (project-wide, 500KB limit). With no cleanup, this store saturates around 5,000 total transactions across all users, after which subscription activation fails globally.

## Residual innerHTML injection in loadCloudPhotos error path

```javascript
.withFailureHandler(function(err) {
  $('cloudLoading').classList.add('hidden');
  $('cloudPhotoGrid').innerHTML = '<p style="color:red;text-align:center;">Gagal memuat: ' + err.message + '</p>';
})
```

In the GAS context, `err` is a server-thrown Error object whose message is set by the backend (`throw new Error(...)` in `getPhotoHistory`). The backend message is developer-controlled today ("Photo history requires an active Pro subscription"), but if any future code path constructs error messages from user input (filename, parameter echo), it becomes exploitable. The fix is trivial: create a `<p>` element and set its `textContent`, matching the pattern used in `renderCloudPhotos`.

## thumbnailUrl does not produce renderable images

`getPhotoHistory` returns:

```javascript
thumbnailUrl: f.getUrl()  // e.g. "https://drive.google.com/file/d/ABC123/view"
```

Setting this as `<img src>` produces a failed load (the `onerror` handler hides the element, so the grid shows no images — just filenames and delete buttons). Options:
- `file.getDownloadUrl()` — returns a short-lived direct-download URL
- Advanced Drive Service: `Drive.Files.get(id, {fields: 'thumbnailLink'})` — resizable thumbnail URL
- Base64 encoding via `Utilities.base64Encode(file.getBlob().getBytes())` — expensive but self-contained

The photo history modal is effectively broken as a visual gallery.

## ScriptProperties accumulation

Every subscription activation generates a transaction ID stored in `ScriptProperties` (the project-wide, shared store). These entries are never deleted. With a JSON payload of ~80-100 bytes per entry, the store saturates around 5,000 transactions across all users, after which `setProperty` throws and subscription activation fails for everyone.

Mitigation options: store transaction IDs in UserProperties instead (per-user, avoids contention), use a single key with a JSON array and prune entries older than the subscription duration, or skip storing generated IDs entirely since the active-subscription check already prevents same-tier replay.
