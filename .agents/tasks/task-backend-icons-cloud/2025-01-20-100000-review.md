# Server-side subscriptions, branded icons, and Drive cloud storage for TrustMark

TrustMark moves from a purely client-side localStorage subscription model to a server-authoritative one backed by Google Apps Script PropertiesService. A new `BackendService.gs` handles subscription activation, payment validation with replay protection, and Google Drive file operations for Pro-tier users. Custom branded SVG icons replace the placeholder URLs, served inline through the existing `doGet` router. The frontend gains a cloud storage card (Pro-only), a photo history modal, and auto-save-to-Drive on download. The localStorage layer is retained as an offline cache with server-wins conflict resolution on load.

**Watch for:** The REST API endpoint (`?page=api`) performs state-changing operations (subscription activation) via HTTP GET, which is vulnerable to CSRF via link/image tags (confirmed). The cloud photo grid renders Drive-returned filenames into `innerHTML` without sanitization, creating a stored XSS vector if a filename contains HTML (confirmed). The `getPhotoHistory` function loads all files into memory before paginating, which will degrade as the folder grows (likely). Payment confirmation falls back to localStorage activation on server error, meaning a network failure during a non-payment still grants the subscription locally (confirmed).

## High-level view

The subscription system uses PropertiesService keyed by email to store tier, expiry, and transaction metadata. The client calls `google.script.run.activateSubscription` on payment confirmation; if that fails for any reason, it falls through to localStorage activation anyway, so the server-side validation is advisory rather than gating.

Transaction replay prevention stores IDs in ScriptProperties, but `activateSubscription` (the primary path called from the client) generates and stores its own transaction ID internally rather than requiring one from the client, so a user can call `activateSubscription` repeatedly with valid tier/amount and get fresh subscriptions each time. The `validatePayment` wrapper that checks client-supplied IDs is wired to the REST API but not to the `google.script.run` path the frontend actually uses.

The Drive integration creates a `TrustMark` folder per user, caches the folder ID in UserProperties, and handles the case where the folder is externally deleted. Deletion verifies parent-folder ownership before trashing. However, `getPhotoHistory` collects all folder files into an array for sorting, meaning response time grows linearly with folder size.

Icons are served as inline SVGs via `ContentService.MimeType.XML`. The manifest declares `purpose: "any maskable"` with `type: "image/svg+xml"`, which works in Chromium 92+ but older Android WebViews may not render SVG manifest icons and will fall back to a generic icon.

<details>
<summary>Issues (7)</summary>

1. **GET-based subscription activation (CSRF)** — The `?page=api&action=activateSubscription` endpoint mutates state via GET. Wrap state-changing actions in a POST check or remove them from the GET router entirely.
2. **Replay protection not on primary path** — `activateSubscription` (called via `google.script.run` from the frontend) does not require or check a client-supplied transaction ID. A user can re-invoke it to extend their subscription. Route the frontend through `validatePayment` or add idempotency checks to `activateSubscription`.
3. **Fallback activates subscription on server failure** — `confirmPayment` calls `saveSubscription(selectedTier, paymentAmount)` in the `withFailureHandler`, granting local Pro access even when the server explicitly rejects the payment. The failure handler should distinguish network errors from validation rejections.
4. **XSS in cloud photo grid** — `renderCloudPhotos` injects `photo.name` and `photo.thumbnailUrl` directly into `innerHTML`. A malicious filename on Drive (e.g., `<img src=x onerror=alert(1)>`) executes arbitrary JS. Use `textContent` for the name and `setAttribute` for the src.
5. **Unbounded file enumeration in getPhotoHistory** — All JPEG files are loaded into an array before slicing for pagination. With hundreds of photos this will hit GAS execution time limits. Consider using a continuation token or limiting the iterator.
6. **No subscription check on getPhotoHistory/deletePhotoFromDrive** — `savePhotoToDrive` verifies Pro status, but `getPhotoHistory` and `deletePhotoFromDrive` do not. A lapsed-Pro user can still browse and delete files via `google.script.run` after expiry.
7. **SVG icon size declaration mismatch** — The manifest declares `sizes: "192x192"` with `type: "image/svg+xml"`. Some install prompts may skip SVGs when they expect raster icons at those dimensions. Low risk but worth noting.

## GET-mutating API endpoint

`Code.gs` routes `?page=api` through `handleApiRequest`, which dispatches on `e.parameter.action`. The `activateSubscription` and `validatePayment` actions mutate server state (write to PropertiesService/ScriptProperties). Because GAS web apps serve everything via `doGet`, any authenticated user who visits a crafted URL like `?page=api&action=activateSubscription&tier=pro&amount=15042` — whether from a link in an email, an `<img>` tag, or a redirect — will have their subscription activated. GAS doesn't support `doPost` for web app HTML service calls in the same deployment easily, but the API route could at minimum validate a session token or be removed if only `google.script.run` is intended for mutations.

## Replay protection gap on the primary activation path

The frontend calls `google.script.run.activateSubscription(selectedTier, paymentAmount)` directly. Inside `activateSubscription`, a new transaction ID is generated and stored, but there's no check preventing the same user from calling `activateSubscription` again with the same tier and a valid amount. Each call overwrites the subscription with a fresh expiry. The `validatePayment` function does check for client-supplied transaction ID reuse, but it's only reachable through the REST API (`?page=api&action=validatePayment`), which the frontend never calls.

## Failure handler grants subscription

```javascript
.withFailureHandler(function(err) {
  // Fallback to localStorage on server error
  saveSubscription(selectedTier, paymentAmount);
  ...
  alert('Terima kasih! Paket ' + selectedTier + ' aktif.');
})
```

If the server throws "Invalid payment amount" or "Invalid tier", the failure handler still calls `saveSubscription` and shows a success message. Server-side validation can never actually reject a payment on the client side. The handler should check whether the error is a network/timeout issue vs. a validation rejection before falling back.

## Stored XSS via Drive filenames

```javascript
item.innerHTML = '<img src="' + (photo.thumbnailUrl || '') + '" alt="' + photo.name + '">'
  + '<div class="cloud-photo-name">' + photo.name + '</div>'
  + '<button class="cloud-photo-del" data-id="' + photo.id + '">&times;</button>';
```

`photo.name` comes from `file.getName()` in the Drive API. Google Drive allows filenames containing `<`, `>`, and quotes. If a user renames a file in Drive to include an HTML payload, it will execute in the app's origin the next time the photo history modal is opened. Since this is a GAS-hosted app, the origin is `script.google.com`, making the XSS particularly impactful (access to other GAS session data). Use DOM APIs (`createElement`, `textContent`, `setAttribute`) instead of innerHTML with unsanitized data.

## Linear scan in getPhotoHistory

```javascript
var allFiles = [];
while (files.hasNext()) {
  allFiles.push(files.next());
}
allFiles.sort(...);
var pagedFiles = allFiles.slice(offset, offset + pageSize);
```

With a folder containing 500+ photos, iterating and sorting on every page request will approach the 6-minute GAS execution limit. The `getStorageInfo` function has the same pattern (iterates all files just to count). Consider caching the count in UserProperties or using the Advanced Drive Service which supports server-side sorting and pagination via continuation tokens.

## Missing tier check on read/delete operations

`savePhotoToDrive` gates on `sub.tier !== 'pro'`. But `getPhotoHistory` and `deletePhotoFromDrive` have no subscription check. Once a Pro subscription lapses, the user can still invoke these functions via `google.script.run` (the frontend hides the card via `updateCloudVisibility`, but the functions remain callable). The backend should verify active Pro status on all Drive operations, not just writes.
