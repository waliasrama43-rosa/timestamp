# TrustMark: Photo timestamp PWA on Google Apps Script

A greenfield PWA that captures photos, renders a timemark overlay (date, location, org, verification code) onto a Canvas, injects EXIF metadata, and offers a QRIS-based payment tier system. The backend is a thin GAS shim that serves index.html and routes manifest/SW requests via query parameters.

Watch for: the QRIS TLV parser silently produces corrupt payloads when encountering sub-TLV fields (tags 26, 51, 62) because it doesn't recurse (**confirmed**); the `UserComment` EXIF field uses a wrong charset header that will produce garbled reads in many viewers (**confirmed**); payment state lives entirely in localStorage and is trivially editable by the user, meaning every "Pro" gate is client-side only (**confirmed**); the service worker registration path will fail under GAS deployment since `sw.js` is not a real URL on the `script.google.com` domain (**likely**).

## High-level view

The GAS backend serves the entire app as a single HTML file. To expose `manifest.json` and `sw.js` with correct MIME types, it uses a `?page=` routing convention. This collides with how browsers resolve relative paths: `navigator.serviceWorker.register('sw.js')` resolves to a non-existent URL on `script.googleusercontent.com`, and `<link rel="manifest" href="manifest.json">` similarly 404s. Both should use `?page=sw` and `?page=manifest` respectively.

The QRIS module implements TLV serialization and CRC-CCITT-FALSE to turn a static merchant QR into a dynamic one with an injected amount. The TLV parser is flat, treating nested TLVs (tags 26, 51, 62) as opaque strings. The insertion sort for tag 54 uses `parseInt(tag)` which produces correct ordering only by coincidence for this specific payload; any non-decimal tag ID (like "5A") would break the comparison. The CRC algorithm itself is correctly implemented.

EXIF injection builds a full IFD structure with GPS DMS coordinates and datetime fields. The `decimalToDMS` conversion and GPS field assignments are correct. The `UserComment` encoding is wrong: piexifjs expects either a raw string (handling encoding internally) or a byte array with the 8-byte charset prefix, but the code passes a plain string with `'ASCII\x00\x00\x00'` prepended as literal characters, producing double-encoding in the output.

Canvas rendering draws a semi-transparent overlay bar at the bottom of the photo with five lines of metadata. The overlay height is `Math.max(h * 0.18, 120)` but fontSize depends on `w`, not `h`. On any image wider than ~1000px, five lines of text exceed the overlay rectangle and render over the raw photo without background contrast. This is the most visible bug.

The payment system is entirely client-side. No server verification, webhook, or callback exists. Any user can write directly to localStorage to unlock Pro permanently.

<summary>Issues (8)</summary>

1. **Flat TLV parser truncates nested tags** — Tags 26, 51, and 62 contain sub-TLVs. The parser reads them as flat strings, which works for passthrough, but `buildTLV` recalculates length from `val.length`. If any inner value contains multi-byte characters or if the parser undershoots due to a decimal-vs-actual-byte mismatch, the output is corrupt. Use a recursive parser or preserve raw bytes.
2. **Tag 54 insertion order is fragile** — `parseInt(tag)` coerces two-digit hex-like strings ("05", "26", "63") to decimal sort values. Tag ordering in EMVCo QR is by specification, not numeric. Hard-code the insertion point or maintain a fixed tag order.
3. **UserComment EXIF encoding is wrong** — piexifjs requires the UserComment value to be either a byte array with the 8-byte charset prefix, or to omit the prefix entirely and let piexif handle it. The current `'ASCII\x00\x00\x00' + payload` produces double-encoding. Remove the prefix or use `piexif.helper.UserComment.dump(payload)` if available.
4. **Service worker won't register under GAS** — `navigator.serviceWorker.register('sw.js')` resolves relative to the page URL (`script.googleusercontent.com/macros/...`). There's no `sw.js` file at that path. The `?page=sw` route exists but doesn't match what the register call requests.
5. **No server-side payment verification** — The "Saya Sudah Bayar" button trusts the client. Payment state is trivially forgeable via localStorage. Implement a GAS-side payment status check or at minimum a signed token.
6. **Canvas overlay overflow on typical photos** — Five text lines at `lineHeight = fontSize * 1.5` where fontSize depends on image width, but overlay height depends on image height. On any image with aspect ratio wider than ~4:3, text overflows the overlay.
7. **PWA manifest `start_url` is "."** — Under GAS exec URLs, "." resolves to the bare domain root, not the app. It should be the full exec URL or omitted entirely.
8. **Logo stored in localStorage as full data URL** — Large logos (several hundred KB) can push localStorage past the 5MB limit and throw, silently breaking all other localStorage state.

## QRIS TLV parser and CRC correctness

The tag 54 insertion logic uses `findIndex(function(t) { return parseInt(t.tag) > 54; })`. The static payload has tags 00, 01, 26, 51, 52, 53, 58, 59, 60, 61, 62, 63. `parseInt('58')` returns 58 > 54, so tag 54 lands before tag 58 (country code)—correct for this specific payload but coincidental. If a tag like "5A" existed, `parseInt('5A')` would return 5, inserting the amount tag at position 1. The EMVCo spec requires tags in a defined order that doesn't map to numeric sorting of their two-character IDs.

The CRC function computes over the QRIS string using `charCodeAt`, which returns UTF-16 code units. QRIS payloads are ASCII-only, so this produces correct byte values. But if a merchant name contained non-ASCII characters (possible in Indonesian names), the CRC would be computed over multi-byte code units rather than the UTF-8 byte sequence a payment terminal expects, producing an invalid checksum.

## UserComment EXIF encoding

The EXIF spec defines UserComment as an 8-byte charset code followed by the comment body. piexifjs handles this encoding internally when you pass a plain JavaScript string. The code prepends `'ASCII\x00\x00\x00'` manually, but JavaScript `\x00` in a string becomes a null character that piexifjs will then wrap in its own encoding layer. The result: tools reading the EXIF will see the charset code appear as literal bytes inside the already-encoded field, producing `ASCII` followed by garbage before the actual JSON payload. Fix: pass just the JSON string without the prefix, or use piexifjs's helper if the version supports it.

## Canvas overlay overflow math

The overlay height is `Math.max(h * 0.18, 120)`. The font size is `Math.max(w * 0.022, 12)`. These are decoupled: height depends on the image's vertical pixels, font size on horizontal pixels. For a standard 4000x3000 phone photo:

- fontSize = 88px, lineHeight = 132px
- 5 lines + padding = 5 * 132 + 2 * 100 = 860px needed
- overlay = max(3000 * 0.18, 120) = 540px available
- Overflow: 320px of text renders over the raw photo

For a 1920x1080 landscape shot: fontSize = 42px, needed height ~411px, available = 194px. The overlay would need to be calculated as a function of `w` (matching the fontSize calculation) rather than `h`. Something like `Math.max(w * 0.022 * 1.5 * 6, 120)` would size the overlay to actually contain the text.

The rendering logic is duplicated verbatim between `renderPreview()` and `doDownload()`. A single shared function would prevent future divergence.

## Service worker and PWA manifest path resolution

The HTML contains:
```html
<link rel="manifest" href="manifest.json">
```
```js
navigator.serviceWorker.register('sw.js')
```

Under GAS, the page URL is `https://script.google.com/macros/s/DEPLOY_ID/exec`. Both relative paths resolve against this, producing URLs like `.../exec/manifest.json` and `.../exec/sw.js` which don't exist. The GAS backend already handles `?page=manifest` and `?page=sw`, so the fix is straightforward: change the href and register path to use query parameters.

Even with corrected paths, `start_url: "."` in the manifest resolves to the GAS domain root (`https://script.google.com/macros/s/DEPLOY_ID/`) rather than the exec endpoint. Installed PWAs would open to a Google error page. The manifest icons point to `via.placeholder.com`, which defeats offline capability and produces a broken install experience.

## localStorage as a trust boundary

The `QuotaExceededError` risk is concrete: the logo upload stores the full base64 data URL in localStorage without any size check. A 2MB photo accidentally uploaded as "logo" becomes ~2.7MB of base64. Combined with favorites (each storing address strings) and subscription data, this can exceed the ~5MB localStorage limit on mobile Safari. The `setItem` call in `initLogo` has no try/catch, so a quota error would halt the logo save and potentially leave the UI in an inconsistent state (preview shown, but data not persisted).
