# Dynamic script loading and camera modal for GAS mobile compatibility (v2)

Replaces static `<script src>` tags with a dynamic loader for GAS HtmlService mobile compatibility, converts the IIFE to a named `initApp()` gated on script load completion, adds a loading spinner, a logo position dropdown, gold/rotated VRF code, and a `getUserMedia` camera modal for desktop with UA-based mobile fallback to native camera picker. Leaflet references are now guarded with `typeof L` checks.

**Watch for:** The `captureFromCamera` function can fire while the video stream is still buffering, producing a black/empty frame if the user clicks immediately (likely). Logo drawn at "bottom-left" or "bottom-right" positions can clip off-screen on landscape crops where height is very small relative to width (possible).

**Verdict**: APPROVED

## High-level view

The three blocking concerns from v1 are resolved. Mobile detection now uses a UA regex rather than `getUserMedia` capability detection, so phones correctly get the native camera picker. Leaflet calls are guarded with `typeof L === 'undefined'` in both `initLocation` and `openMapModal`, gracefully degrading to a text message. A full-screen loading spinner (`appLoader`) is shown until `initApp` fires, eliminating the dead-button window.

The logo draw-order places the logo before the overlay background `fillRect`, which is correct for top positions but means bottom positions rely on the math keeping `logoY` above `overlayY` — a tight margin on small images that can go negative on extreme aspect ratios.

The remaining EXIF gap on camera-captured photos is inherent to canvas-exported JPEGs and was acknowledged as an accepted limitation.

<summary>Issues (2)</summary>

1. **Capture on unbuffered video** — `captureFromCamera` reads `video.videoWidth` / `video.videoHeight` immediately on click. If invoked before the stream delivers its first frame, both dimensions are 0 and the canvas is 0×0, producing an empty data URL that breaks downstream image loading. Guard with a check that `video.videoWidth > 0` before capturing, or disable the capture button until `loadeddata` fires.
2. **Logo/overlay overlap on small images** — For bottom-left/bottom-right positions, `logoY = overlayY - logoH - logoPad`. On landscape crops where height is small relative to width, `logoY` can go negative (logo clips off-screen). Consider clamping `logoY` to `Math.max(logoPad, ...)`.

## Capture timing on cold video stream

`openCameraModal` calls `getUserMedia` and then `video.play()`, but doesn't disable the capture button or wait for the stream to produce frames. The capture button is active the instant the modal opens:

```javascript
function captureFromCamera() {
  var video = $('cameraVideo');
  var canvas = document.createElement('canvas');
  canvas.width = video.videoWidth;
  canvas.height = video.videoHeight;
  var ctx = canvas.getContext('2d');
  ctx.drawImage(video, 0, 0);
  ...
}
```

If `video.videoWidth` is still 0 (stream acquired but no frame decoded yet), the canvas is zero-sized. `canvas.toDataURL` on a 0×0 canvas returns `data:,` — an empty string that will break the downstream `new Image()` load and leave the app in a broken state (`state.photoImage` never set, preview blank, download button enabled but non-functional).

A minimal fix: listen for the `loadeddata` event on the video element and only enable `btnCameraCapture` after it fires.

## Logo draw-order vs. overlay band on extreme aspect ratios

For bottom positions, the logo is placed at `overlayY - logoH - logoPad`. On very small images (say 400px tall), `overlayY` could be as low as `h - 120 = 280`. With `logoH = w * 0.06` and `logoPad = padding * 2 = w * 0.05`, the logo sits at roughly `280 - 24 - 20 = 236px` for a 400×400 image — minimal clearance. On landscape crops where height is very small relative to width (e.g., a 1200×300 banner), `logoH` grows with width while available vertical space shrinks, and `logoY` goes negative — the logo renders entirely off-canvas with no clamping.
