# Dynamic script loading and camera modal for GAS mobile compatibility

Replaces static `<script src>` tags with a dynamic loader to work around Google Apps Script's HtmlService stripping external scripts on mobile. Converts the IIFE app wrapper to a named `initApp()` called after all CDNs load. Adds a logo position dropdown (four corners), changes the VRF code to gold/smaller/rotated, and introduces a `getUserMedia`-based camera modal for desktop with a file-input fallback for mobile.

**Watch for:** The `getUserMedia` availability check doesn't distinguish desktop from mobile — most modern mobile browsers also expose `navigator.mediaDevices.getUserMedia`, so the file-input fallback may never trigger on mobile (confirmed). If Leaflet fails to load, `initApp` still runs and `L.map()` throws an unguarded ReferenceError that crashes the entire app (confirmed). The VRF code length doubled to 16 characters but the vertical text clamp addresses the prior review's concern only partially — on images where `overlayHeight` hits the 120px floor, the re-scaled font becomes unreadably small rather than clipping (likely).

## High-level view

The dynamic script loader fires all three CDN fetches in parallel and gates `initApp()` on all completing. Because `onerror` also increments the counter, a failed fetch still triggers app initialization — the right call for resilience, except the downstream code (specifically Leaflet's `L.map()`) has no null guard and will throw immediately, halting the entire DOMContentLoaded handler.

The `getUserMedia` detection heuristic (`navigator.mediaDevices && navigator.mediaDevices.getUserMedia`) is treated as a desktop-vs-mobile signal, but it's actually a capability signal. Every recent Android and iOS browser passes this check, meaning mobile users will see the video modal instead of the native camera picker. The native picker is preferable on mobile because it handles permissions, orientation, and EXIF metadata natively.

The camera modal manages the media stream lifecycle correctly — tracks are stopped on close — but captured frames lose all EXIF data. The regular `handlePhoto` path preserves EXIF from the uploaded JPEG; the camera capture path sets `state.originalExif = null`, so downloaded photos from camera capture will lack embedded geolocation even if the app's overlay shows GPS coordinates.

The prior review's watermark color concern (white-on-white) has been addressed — now `#1B3A5C`.

<details>
<summary>Issues (5)</summary>

1. **getUserMedia on mobile overrides native camera picker** — `navigator.mediaDevices.getUserMedia` exists on modern mobile browsers, so the file-input fallback path is effectively dead on mobile. Use a more specific heuristic (e.g., check `'ontouchstart' in window` combined with screen size, or offer both options) to preserve the native camera experience on phones.
2. **Leaflet crash on CDN failure** — If `leaflet.js` fails to load, `initLocation()` calls `L.map()` which throws an uncaught ReferenceError, halting all subsequent initialization. Wrap map init in a try/catch or guard with `typeof L !== 'undefined'`.
3. **Camera capture drops EXIF metadata** — `captureFromCamera` creates a JPEG from canvas with no EXIF. The download path skips GPS/datetime injection when `state.originalExif` is null, so the output file has no embedded geolocation. Consider constructing a fresh EXIF object from the browser's geolocation data.
4. **VRF font shrinks to illegibility on small images** — When `overlayHeight` hits the 120px floor, the VRF text (16 chars) is clamped by reducing font size proportionally. At that floor, the font could shrink to ~5px. Add a minimum font size threshold below which the VRF code is truncated or hidden.
5. **No loading indicator while CDN scripts fetch** — `loadScripts()` runs immediately but `initApp()` fires only after all three CDNs respond. On slow connections the user sees a rendered page with non-functional buttons for several seconds. A loading spinner or disabled state would prevent confusion.

## getUserMedia detection is not a desktop signal

The branching logic in the camera button handler:

```javascript
if (navigator.mediaDevices && navigator.mediaDevices.getUserMedia) {
  openCameraModal();
} else {
  cameraInput.click();
}
```

This checks for API availability, not device form factor. Chrome on Android, Safari on iOS 14+, and Firefox Mobile all expose `getUserMedia`. The else branch — which triggers the native file picker with `capture="environment"` — is the better UX on phones because it uses the OS camera app (handles orientation, HDR, burst, EXIF embedding). The modal with a raw `<video>` feed lacks these niceties.

A more reliable heuristic would combine `navigator.maxTouchPoints > 0` with a viewport-width check, or explicitly offer both capture modes behind a long-press or secondary button.

## Script loader resilience gap

The loader counts errors alongside successes, so `initApp()` runs even when a CDN is unreachable. But `initLocation()` immediately references `L.map()` without a guard:

```javascript
miniMap = L.map('miniMap', { ... }).setView([-6.2, 106.8], 5);
```

If Leaflet didn't load, this throws `ReferenceError: L is not defined`, which propagates up and kills the rest of the initialization chain (datetime, payment, settings). The QRCode library is already guarded (`typeof QRCode !== 'undefined'`), and piexif is inside a try/catch, but Leaflet is unprotected. Adding `if (typeof L === 'undefined') return;` at the top of `initLocation` would contain the failure to just the map feature.

## Camera capture loses embedded metadata

Canvas-exported JPEGs contain no EXIF. The `captureFromCamera` function sets `state.originalExif = null` explicitly. In the download path, the code checks `state.originalExif` and attempts to write GPS coordinates into it — with null, this branch is skipped entirely. The final downloaded JPEG from a camera capture contains no embedded geolocation even though the overlay visually shows coordinates from the browser's geolocation API.

For a forensic/legal timestamp app, the absence of embedded EXIF in camera-captured photos is a functional gap compared to photos uploaded via the native camera app (which embeds GPS, orientation, and datetime natively).

## VRF vertical text scaling at small overlay sizes

With `VRF-` plus 12 characters (16 total) at monospace, the rendered width at base size is roughly `16 * vrfFontSize * 0.6`. The clamping logic reduces font size proportionally when text exceeds the overlay height:

```javascript
var maxVrfWidth = overlayHeight - padding * 2;
if (vrfMetrics.width > maxVrfWidth) {
  vrfFontSize = vrfFontSize * (maxVrfWidth / vrfMetrics.width);
}
```

When `overlayHeight` hits its 120px floor on small images, and base `vrfFontSize` is already at `max(w*0.022, 12) * 0.55 ≈ 5-6px`, further scaling pushes it below legibility. There's no minimum threshold — the font can go arbitrarily small without being hidden or truncated.
